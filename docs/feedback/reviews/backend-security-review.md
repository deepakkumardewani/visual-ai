## ADVISORY

1. Low · alert email flooding · `services/feedback-service.ts:151-159`. Any user can POST a 1-star popup or `bug` 10 times per 10 min (no eligibility claim required to submit), and each sends a synchronous alert to `FEEDBACK_NOTIFY_EMAIL` in send mode; many free accounts multiply this. Fix: cap alerts per user (e.g. one per user per hour via a Redis key) or a global alert budget, and send off the request path.
2. Low · client-supplied context shown as fact in alerts · `feedback-service.ts:128-129`, `FeedbackAlert.tsx:60-61`. `context.plan` and `context.route` come from the client, so an attacker can make an alert read "Plan: pro" or put a URL in "Page:" that mail clients auto-link. Fix: derive plan server-side from the user record; label client context as "reported".
3. Low · unbounded `page` · `packages/shared/src/schemas/feedback.ts:75`, `feedback-service.ts:211`. very large values (e.g. `page=1e300`) push `skip` past int64 and the driver throws a 500 whose message reaches the client via the global handler. Admin-only. Fix: `.max(FEEDBACK_ADMIN_MAX_PAGE)` (e.g. 10000).
4. Low · preview HTML with user emails/messages written to disk on staging · `lib/feedback/mailer.ts:42`. The guard only checks `production`, so a staging host in log mode keeps PII files indefinitely. Fix: write previews only when `NODE_ENV` is `development` (allowlist instead of denylist).
5. Low · tests load the developer `.env` (`vitest.config.ts` `setupFiles: ["dotenv/config"]`). If someone sets `FEEDBACK_EMAIL_MODE=send`, any future test that reaches the real mailer unmocked would send. Fix: in `deliverFeedbackEmail`, force log when `NODE_ENV === "test"`.
6. Info · weekly digest cron (`utils/cronJobs.ts`) has no distributed lock, so N API instances send N digests. Fix: guard with a Redis `SET NX` lock keyed by the ISO week.
7. Info (pre-existing, out of scope) · `GET /users` (`apps/api/src/routes/users.ts:28-34`) returns every user document (emails, credits, referrals, now `feedback.*`) to any authenticated caller; `GET /users/:id` (`users.ts:37-51`) lets any authed user read any other user's record by Clerk id (IDOR). Confirmed. Fix: delete `GET /users` or gate it with `requireAdmin`; make `/users/:id` require `req.auth.userId === id` (or admin).
8. Info (pre-existing) · the global error handler returns `err.message` for non-HTTP 500s (`apps/api/src/app.ts:112-114`), leaking driver/internal messages. Fix: send a generic message when `!isHttpError(err)`.

## Summary

The feedback backend has no exploitable issues. All seven routes sit behind Clerk `requireAuth` and the per-user rate limiter. Admin routes additionally pass `requireAdmin`, which fails closed when `ADMIN_USER_IDS` is empty. Zod validation blocks operator injection in the admin query filters and caps every stored string. React Email escapes user text, subjects carry no user input, and the mailer defaults to log mode with no preview files in production. The advisories cover hardening: an alert-email budget, server-side plan in alerts, a `page` cap, a dev-only preview write and a test-mode mail guard. Separately, two pre-existing problems in `users.ts` let any signed-in user list all users and read any user's record. They should be fixed outside this feature. Non-security notes: the CORS `methods` list (`app.ts:46`) omits `PATCH`, so a cross-origin admin `PATCH /feedback/admin/:id` would fail preflight unless the web app reaches the API same-origin (collections already uses PATCH, so check how it works today). Also, one rate-limit bucket covers eligibility, submit and admin calls, so an admin browsing the list can hit 429 after 10 requests in 10 minutes.
