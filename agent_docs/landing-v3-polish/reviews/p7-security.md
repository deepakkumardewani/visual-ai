## BLOCKING

- P7.1 · [security] · apps/web/src/utils/safeRedirect.ts:13-15 · Open redirect through dot-segment normalisation (traced: the function was run in node). The prefix checks run on the raw string, but the returned value is the _normalised_ `url.pathname`. So `/signin?redirect=/.//evil.com` returns `//evil.com`. The same happens for `/%2e//evil.com`, `/a/..//evil.com`, `/./\evil.com` and `/x/../\evil.com`, and each of those resolves to `https://evil.com`. That value goes to Clerk as `forceRedirectUrl` and `signUpForceRedirectUrl` (Signin.vue:18-20). Mitigation (inferred from the bundle, not run in a browser): clerk-js 5.127 sets a default `allowedRedirectOrigins` of the current origin plus the Clerk frontend API's eTLD+1, so Clerk should fall back to the default URL today. The app sets no `allowedRedirectOrigins` itself, so the only first-party guard is broken, and safety depends on an unconfigured library default. · Fix: after parsing, return undefined when `url.pathname.startsWith('//')`, or check the returned string again with the same `//` and `/\` tests. Add unit cases for `/.//evil.com`, `/%2e//evil.com`, `/a/..//evil.com` and `/./\evil.com`. Also set `allowedRedirectOrigins: [window.location.origin]` in plugins/index.ts as defence in depth.
